Проект представляет собой сервис для автоматической сегментации держателей кредитных карт. На основе транзакционных данных (покупки, снятия наличных, платежи) модель выделяет 5 типологий клиентов (например, «Ответственные плательщики», «Любители наличных»). Сервис предоставляет REST API для получения прогноза в реальном времени, выдавая не только номер кластера, но и интерпретируемую бизнес-рекомендацию (уровень риска, стратегия взаимодействия). Решение контейнеризировано в Docker и включает базовую наблюдаемость.

## 2. Постановка задачи и контекст


**Предметная область**

Банковский сектор, розничное кредитование. Потенциальные пользователи сервиса — маркетологи и риск-менеджеры банка.

**Задача:** Сегментировать клиентскую базу для персонализации маркетинговых предложений и управления кредитными рисками. Вместо массовой рассылки, банк может таргетировать конкретные сегменты: например, предлагать увеличение лимита «Ответственным клиентам» или ограничивать снятие наличных для сегмента с высоким риском.

**Формулировка задачи в терминах ML/ИИ:**

Задача **неконтролируемого обучения (Unsupervised Learning)** — кластеризации.
   - **Входные данные:** JSON с финансовыми данными клиента (баланс, частота покупок, доля полных оплат и т.д.).
   - **Выходные данные:** JSON с результатами прогноза (номер кластера + интерпретируемая бизнес-рекомендация (уровень риска, стратегия взаимодействия)).
   - **Ограничения:** Модель должна быть интерпретируемой (банку важно понимать, *почему* клиент попал в этот сегмент) и быстрой (инференс < 100 мс).

**Целевые метрики качества:**

Так как истинных меток нет, используются внутренние метрики кластеризации:
1.  **Silhouette Score:** Оценивает, насколько объект похож на свой кластер по сравнению с другими. Цель: максимизация (ближе к 1).
2.  **Calinski-Harabasz Score:** Отношение межкластерной дисперсии к внутрикластерной. Цель: максимизация.
3.  **Davies-Bouldin Index:** Оценка среднего сходства между каждым кластером и его наиболее похожим соседом. Цель: минимизация (ближе к 0).

Выбор этих метрик обусловлен необходимостью найти компактные и хорошо разделенные группы клиентов.

## 3. Данные

1. **Источник данных:**
   - Используется открытый датасет **"Credit Card Dataset for Clustering"**
   - доступен на Kaggle: `https://www.kaggle.com/datasets/arjunbhasin2013/ccdata`.
   - Данные обезличены, содержат информацию о поведении ~8900 клиентов.  
   - Файл лежит в репозитории: `data/credit_cards_dataset.csv`.

2. **Структура данных:**

   Датасет содержит 18 числовых признаков:
   - CUST_ID - Идентификатор клиента
   - BALANCE - Остаток на счёте
   - BALANCE_FREQUENCY - Частота обновления баланса
   - PURCHASES - Сумма покупок
   - ONEOFF_PURCHASES - Разовые покупки (без рассрочки)
   - INSTALLMENTS_PURCHASES - Покупки в рассрочку
   - CASH_ADVANCE - Общая сумма снятых наличных
   - PURCHASES_FREQUENCY - Частота покупок
   - ONEOFF_PURCHASES_FREQUENCY - Частота разовых (без рассрочки)
   - PURCHASES_INSTALLMENTS_FREQUENCY - Частота покупок в рассрочку
   - CASH_ADVANCE_FREQUENCY - Частота снятия наличных
   - CASH_ADVANCE_TRX - Количество операций снятия наличных
   - PURCHASES_TRX - Количество покупок
   - CREDIT_LIMIT - Кредитный лимит
   - PAYMENTS - Сумма платежей для погашения долга
   - MINIMUM_PAYMENTS - Минимальные обязательные платежи
   - PRC_FULL_PAYMENT - Процент месяцев, в которых клиент погасил задолженность полностью (а не минимальным платежом)
   - TENURE - Срок обслуживания

3. **Предобработка и EDA:**

   Основные шаги реализованы в ноутбуке `notebooks/exp_01_eda.ipynb`:
      1.  **Очистка:** Удален идентификатор `CUST_ID` (не несет информации для кластеризации). Пропуски в `CREDIT_LIMIT` и `MINIMUM_PAYMENTS` заполнены медианой, так как распределение этих признаков асимметрично.
      2.  **Анализ распределений:** Гистограммы показали сильную правостороннюю асимметрию (skewness) для финансовых признаков.
      3.  **Трансформация признаков:**
         *   Применено **логарифмическое преобразование** (`log1p`) к денежным колонкам для уменьшения асимметрии и сжатия выбросов.
         *   Использован **StandardScaler** для приведения всех признаков к единому масштабу (критично для K-Means).
      4.  **Отбор признаков (Feature Selection):**
         *   Построена матрица корреляций. Выявлена высокая мультиколлинеарность (например, `PURCHASES` и `PURCHASES_TRX` коррелируют на 0.89).
         *   Для устранения дублирования информации оставлены 8 ключевых признаков:
            *   Финансы: `PURCHASES`, `CASH_ADVANCE`, `INSTALLMENTS_PURCHASES`.
            *   Частота: `PURCHASES_FREQUENCY`, `CASH_ADVANCE_FREQUENCY`.
            *   Дисциплина: `PRC_FULL_PAYMENT`.
            *   Статус: `CREDIT_LIMIT`, `TENURE`.

## 4. Модели и подходы

Опишите, какие модели вы пробовали и как развивался ваш подход:

1. **Базовые (baseline) модели:**

   В качестве baseline был взят алгоритм **K-Means** с дефолтным количеством кластеров $k=4$.
   *   **Результат:** Silhouette Score ≈ 0.28. Кластеры получились размытыми.

2. **Улучшенные модели и эксперименты:**
   - какие модели, архитектуры или настройки были добавлены поверх baseline;
   - какие гиперпараметры/настройки оказались важными;
   - какие эксперименты вы проводили (например, фичи, архитектуры, регуляризация, обучающие режимы).

   Было проведено сравнение трех семейств алгоритмов кластеризации (ноутбук `notebooks/exp_02_models.ipynb`):

   1.  **K-Means (Tuned):**
      *   Проведен подбор гиперпараметров через `ParameterGrid`: `n_clusters` [3..7], `init` ['k-means++', 'random'], `n_init` [5..12].
      *   Использован метод "Локтя" (Elbow Method) и график Silhouette Score. Оптимальное количество кластеров оказалось равным **5**.
      *   Лучшая конфигурация: `n_clusters=5`, `init='k-means++'`, `n_init=10`.

   2.  **DBSCAN:**
      *   Алгоритм плотностной кластеризации.
      *   **Проблема:** DBSCAN выделил много точек как шум (-1) из-за разной плотности кластеров. Это сделало сегментацию неполной, что неприемлемо для бизнеса (каждый клиент должен получить рекомендацию).

   3.  **Agglomerative Clustering (Hierarchical):**
      *   Использовалась линкедж-стратегия 'ward'.
      *   Показал хорошие результаты, но вычислительно сложнее на больших объемах данных по сравнению с K-Means.

## 6. Архитектура решения и сервис

Опишите, как из модели получился работающий сервис:

1. **Архитектура пайплайна:**
   1.  **Data Layer:** Загрузка CSV, очистка пропусков (медиана), удаление ID.
   2.  **Feature Engineering:** Логарифмирование skewed-признаков, выбор 8 целевых колонок, масштабирование (StandardScaler).
   3.  **Model Layer:** Загрузка обученного K-Means (`joblib`). Предсказание метки кластера.
   4.  **Business Logic:** Маппинг метки кластера (0-4) на словарь профилей (`CLUSTER_PROFILES`), содержащий типологию, уровень риска и рекомендацию.
   5.  **Service Layer:** FastAPI оборачивает логику предсказания в HTTP эндпоинт.

2. **API и endpoints:**

   Реализован на фреймворке **FastAPI**:
   - `GET /health`: Проверка доступности сервиса и загруженности модели.
   - `POST /predict`: Принимает JSON с данными клиента. Возвращает JSON с `cluster_id`, `typology`, `risk_level`, `recommendation`.
   - `GET /metrics`: Экспорт метрик Prometheus (счетчики запросов, гистограмма времени ответа).

3. **Технологический стек:**
   - **ML:** Scikit-learn (KMeans, StandardScaler), Pandas, NumPy.
   - **Web:** FastAPI, Uvicorn.
   - **Config:** PyYAML, python-dotenv.
   - **Ops:** Docker, Docker Compose, Prometheus Client.
   - **Testing:** Pytest.

## 8. Ограничения и дальнейшая работа

Текущие ограничения
1.  **Статичность профилей:** Описание кластеров (`CLUSTER_PROFILES`) задано экспертно на основе анализа центров одной конкретной модели. При переобучении на новых данных центры могут сместиться, и описания станут неточными.
2.  **Отсутствие обратной связи:** Сервис не сохраняет историю предсказаний и не учитывает, привела ли рекомендация к конверсии.
3.  **Безопасность API:** Нет авторизации (API Key/OAuth), любой пользователь может отправлять запросы.

Планы развития
1.  **Динамическая интерпретация:** Реализовать автоматическую генерацию описания кластера на основе средних значений признаков в момент инференса.
2.  **Мониторинг дрейфа данных (Data Drift):** Добавить проверку распределения входящих данных. Если новые клиенты стали сильно отличаться от обучающей выборки, модель нужно переобучить.
3.  **A/B Тестирование:** Развернуть две версии сервиса с разными моделями и сравнивать эффективность маркетинговых кампаний.
